# 外部Editorの共同編集契約案

[参照 Host の起動と接続](extension-collaboration-reference.md)

対象は OEP `90ffea1b` と [open-editor-template `78f29d4`](https://github.com/ryo0221/open-editor-template/tree/78f29d4)。状態は提案です。以下は追加する契約と受入条件の案であり、実装・検証はこれからです。数値の上限と期間は、運用前に計測して決める初期値です。

## 宣言と共有操作の入口

1. **新しい共同編集 add-on が既存の操作宣言を参照する。** manifest に対応する `OperationDeclaration` の ID・版、共有用 codec の entry とハッシュを列挙する。入力 schema は宣言から引く。`operations@0-draft` の提案・単独編集契約は維持する。カード例は既存の `rename-card` に加え、追加・説明や色の編集・削除・並べ替えを宣言する。既存宣言と入力形式や意味が変わる場合は操作の版を上げる。
2. **Extension が純粋な codec を提供する。** `validate` は内容の型と不変条件を判定する。`plan(declarationId, version, input, baseContent)` は宣言した操作の入力を、読み取り元の内容に対する Action 列へ変換する。`resource(content,key)` は資源の値を返し、`apply(content,action)` は変更後の内容と `required`・`touched`・`targets`・`inverse` を返す。共有用 entry にはアンカーの検証・移動も含める。Host は登録した codec を実行して必要な条件を導出し、クライアントが条件を省いた場合は拒否する。[DomainCodec と Effect](../packages/collaboration-core/src/contracts.ts)
3. **wire には操作宣言の ID・版と JSON 入力を載せる。** 関数を含む `ScopedHost.execute(EditorCommand)` は単独編集用。共通化するのは内部の純粋な編集処理。Host は指定版の宣言で入力を検査し、`baseRevision` の内容で `plan` を実行して Action 列を作る。base への `apply` で導出した条件を、送信された条件および現在の資源と照合する。次に同じ Action 列を現在の内容へ一括適用する。現在の内容への `apply` で必要な資源の集合が base のときと変われば、操作全体を拒否する。base を復元できなければ再同期を求める。ブラウザーの楽観表示は Host の確定結果に同期し、本人の未反映入力を残す。現行の `PreparedOperation.commit` は内容全体を `base` と比較するため共有経路からは呼ばない。AI の preview は共有の読み取り条件を保持し、採用時に同じ `plan`・codec・権限・条件を通す。提案者と採用者を記録する。[現行の操作準備と確定](../packages/extension-runtime/src/index.ts)
4. **外部Editorは protocol 2・envelope schema 1 で `ext:<manifest id>` を使う。** protocol 1 の domain は既存の9種を維持する。接続時に版を交渉し、固定した登録情報に一致する domain だけを受け付ける。操作・receipt の照会先・snapshot・履歴・checkpoint・保存版のメタデータまで同じ成果物と domain に結び付ける。一つの共有下書き世代は一つの manifest ID に結び付く。同じ artifactKind の別 Editor はこの世代に同席できず、ID の変更も世代移行として扱う。既存の native JSON と保存済みのハッシュを変更する必要はない。

## 何を読んで、何を変えたか

Surface は再送用の `operationId`、読んだ confirmed snapshot の `baseRevision` と、必要なキーの単調増加 stamp・canonical 値の fingerprint を操作に含める。Host は認証済み接続、読み取り元の版、条件のキーと値を検証し、現在の各資源と照合する。ほかのカードだけが変わった場合は受理できる。同じ欄が一度変わって元に戻った場合も stamp が進むため競合する。削除・再作成をまたいで stamp を再利用しない。[共同編集の契約](collaboration-contract.md)

| カード操作 | 必要な資源と確定時の効果                                                                                                                                             |
| ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 欄を編集   | カードの存在と変更する欄を読む。変更した欄だけに書く。削除判定用のカード全体の読み取り条件には子の変更も反映する。                                                   |
| 追加       | 選んだ安定 ID の不在を条件に末尾へ追加し、存在・内容・順序を更新する。既存の並びは前提にせず、異なる ID の追加は確定順に並ぶ。                                       |
| 削除       | 対象カード全体の子孫 stamp とその ID の並びへの所属だけを条件に取り除く。逆操作には削除した内容と確定直前の先行カードの ID・存在 stamp（先頭は先頭の印）を記録する。 |
| 並べ替え   | UI の上下ボタンが、見ている版での ID の完全な並びを生成する。順序を一つの資源として読む・書く。確定時に現在の ID の完全な置換かを検証する。                          |

Host は操作を直列に評価し、全体の不変条件まで成立した変更だけを一括確定する。順序を読んだ並べ替えは、先に追加が確定すれば競合する。並べ替えが先なら、後の追加は新しい順序の末尾に入る。入力は canonical JSON 20 KiB、宣言はパッケージあたり16操作まで（他の schema 上限も継承）、wire envelope は 1,000,000 文字まで。カード数は確定後に最大100枚とする。[操作の上限](../packages/extension-runtime/src/operations.ts)

## 権限と実行環境

現在の `ExtensionRegistry` は信頼済みコード用の in-process prototype で、単一の admission と ESM entry を使う。共有対応では UI と codec を別 entry・別ハッシュ・別 admission にし、Host が両方の固定値を照合する。確定側では UI を import しない。codec は隔離プロセス内の QuickJS で、JSON のコピーのみを受け渡す。`validate` に加え、共有に使う `checkInput`・`plan`・資源解決・適用・逆操作生成のすべてを決定的な ECMAScript に限定し、ネットワーク、ファイル、資格情報、時計、乱数、動的 import、Host へのコールバックを提供しない。初期予算案は1トランザクション累計 CPU 50 ms、VM ヒープ16 MiB、再入0回。Host が割込みとプロセス終了を管理し、予算超過は部分反映せず拒否する。累計には入力検査、base と現在の内容への適用、逆操作生成、最終 validate も含む。再入0回とは codec 実行中の Host 呼び戻し・再ディスパッチを禁止すること。QuickJS は新規依存の候補であり、実装時に最大入力で計測して採否を決める。ブラウザーでは予測のみを許し、条件や fingerprint が異なれば確定せず再同期する。Intl、localeCompare、toLocale 系、Date、Math.random、eval、Function を禁止し、並べ替えでは locale に依存しない全順序を明示する。

manifest の `artifact:read` と本人の現在の閲覧許可を満たす接続のみ、snapshot・履歴・receipt・presence を取得できる。書き込みはさらに `artifact:write`、認証済み Principal の `writable` とHost が導出した対象 ID 全件に対する scope をすべて要求する。確定・Undo/Redo・提案採用・保存時にも再検証する。権限失効時は購読を閉じ、表示・キャッシュを消去する。回収対象は端末上で本人が入力した値だけ。元の snapshot、開いた時点の欄値、他者の内容、before 値や逆操作を含む envelope は渡さない。

`Principal.scopes` は成果物内の対象 ID の集合。カード例では一覧の予約 ID を `@order` とする。カード ID は英数字で始まるため、形式上衝突しない。新規追加の認可対象は一覧 ID、欄編集は既存カード ID、削除はカードと一覧、完全な並べ替えは一覧と並べ替え対象のカードすべてとする。Host は現在の内容で新規 ID の不在を検証する。一覧への追加権限から既存カードの編集権限を派生させない。Undo/Redo でも実際に実行する逆操作の対象を検査する。[現行の対象照合](../packages/collaboration-core/src/authority.ts)

クライアントの checkpoint は本人が実際に入力した値と、再送 envelope・before・snapshot を別々に保存する。失効時の回収は前者のみに限定し、後者を破棄する。オフラインから戻ったときも再認証してから後者を表示する。

## Surface、再送、Undo

共同編集を交渉できた Surface にだけ専用 handle を渡す。confirmed snapshot と receipt・接続状態の購読（初期版と以後の順序付き通知）、操作の送信・結果照会、Undo/Redo、revision 指定保存と保存結果照会を提供する。欠番があれば再取得する。draft.1 の `ScopedHost` とカード例の 200 ms polling は単独編集用のままとする。draft.2 の `inputs@0-draft` は対応時に未確定入力の把握に利用できるが、再送・失効後の回収は別途この契約で扱う。カーソル・選択は一時配信し、アンカーが消えれば orphan として要素上の表示を消す。保存には含めない。

Host が世代内で一意の session 用名前空間を発行する。送信元が初回送信前にその名前空間と UUID から operationId を作り、正確な要求とともに保持する。一意性は成果物の共有下書き世代内（参加者をまたぐ）。Host は認証後にその世代・ID・所有者・canonical 要求を照合する。同一要求には拒否を含む元の receipt、同じ ID の異なる内容には `protocol-error` を返す。所有外の名前空間への送信は ID の存在を調べず、自分の ID を異なる内容で再使用した場合と同じ protocol-error・本文を返す。他者の receipt 照会も存在しない ID と同じ応答にする。共有下書きを閉じるまで、Host は照合記録を再起動・履歴圧縮後も保持する。この保持は Host への追加要件である。

世代を閉じた後も、本人の receipt は7日間照会できる。Host は旧世代の受理・拒否の結果を、世代切替と原子的に照会専用へ移す。閉じた世代への再送は再適用しない。再接続した Surface は、応答を失った操作について旧世代の receipt を先に照会する。受理済みなら未送信一覧から外し、拒否済みなら理由と本人入力を表示する。照会期限が過ぎて結果が分からない場合は「結果不明」と表示し、新世代への自動再送は行わない。

送信制限の初期案は、session ごとに新規操作を毎秒10件、瞬間最大20件とする。さらに、同一 actor の新規要求が1世代で拒否500件に達したら、その actor の新規送信を一時停止する。別タブを開いてもこの枠は共有する。頻度超過・停止中の要求は操作の受付前に返し、世代の照合記録の件数に加算しない。receipt 照会と既存要求の再照合は引き続き利用できる。

逆操作は codec が実際に読んだ変更前の値から欄・構造単位で作る。Host が本人の受理済み操作と確定直後の資源条件に結び付け、現在も条件が合う場合だけ適用する。追加の Undo は削除と同じく対象カードの子孫 stamp と並びへの所属を照合し、その ID だけを除く。削除の Undo は記録した先行カードの直後（元が先頭なら先頭）へ戻す。先行カードの消失・再作成、戻す ID の再利用は `undo-conflict` とする。明示的な並べ替えの Undo は順序全体を条件にする。Redo は成功した Undo の逆操作に同じ検査を行う。所有は `actor + session`。新世代には履歴を引き継がない。リモート変更は単独編集用の履歴に積まない。

同じ session は、正当な再読み込みを証明できた新接続が引き継ぐ。Host は本人・世代・session に結び付けた短命の一回限りの再開 token を原子的に消費し、接続世代を進める。その時点から旧接続の書き込み・Undo・Redo を拒否して接続を閉じる。切断通知が遅れても、旧接続は編集を確定できない。引き継いだ接続だけが同世代の履歴を使える。

複製タブは checkpoint や `sessionStorage` の token もコピーし得るため、token の所持だけでは元タブの再読み込みと認めない。Host のブラウザーアダプターが元タブからの再読み込みへの引継ぎを識別できた場合にだけ token を使う。識別できない環境、複製タブ、期限切れ・消費済み token は新規 session で開き、元の Undo 履歴は渡さない。この場合は既存の接続も切らない。

## 保存とパッケージ更新

共有の下書きの live revision は操作の受理順。画面の「反映済み」は `accepted`（`durable: false`）に対応する。confirmed snapshot は指定 revision の確定内容。利用者が保存して得る固定版が `ArtifactVersion` である。[現行の保存境界](../packages/collaboration-core/src/versions.ts)

現行の `saveConfirmedVersion` は呼出時の snapshot を使い、`commitVersion` は呼出ごとに版を作る。新しい保存入口は成果物・世代・revision・内容ハッシュ・期待する保存先の版・保存要求 UUID を取る。利用者が見ていた revision が復元範囲内なら保存を受け付ける。A が r4 で保存を押し、到着時に r5 へ進んでいても、指定した r4 の内容ハッシュと保存先の親版が一致すれば r4 を保存する。Host は受付時に対象の snapshot を固定し、その後の編集や圧縮の影響を受けないようにする。復元範囲外なら「この版は保存できません」と伝え、最新の下書きを開いて保存するかを本人が選ぶ。保存の確定時には期待する親 versionId を CAS で照合する。親版が変わっていた場合は競合を返し、本人が先に保存された版を見比べてから判断できるようにする。認可後は保存済み要求の照合を revision・親版の検査より先に行う。保存要求の照合と固定版の作成を同じ永続トランザクションで行い、再送には、圧縮後も元の versionId を返す。同一 ID の要求変更は拒否する。保存結果の照合記録は固定版とともに保持する。保存中に届いた編集は次の保存対象になる。

Host は現在の checkpoint と、遅れた編集の `plan` および保存に使う直近最大256 revision の復元範囲を公表する。圧縮で範囲外になった base は再同期とし、receipt は別に照合する。世代は明示的な共有終了、移行成功、または照合記録1万件で閉じる（初期上限案。受け付けた要求の拒否も数え、送信制限で受付前に返した要求は数えない）。上限時は新規要求の受付を止め、受付済み保存を完了または中止して結果を記録し、最新の下書きと stamp を checkpoint にして原子的に次世代を開く。これは利用者による保存ではない。クライアントには世代切替と Undo 履歴の終了を知らせ、未反映入力を保つ。世代 ID は再利用しない。閉鎖後の編集要求は世代不一致で拒否する。操作別の記録は照会専用として7日間保持し、その後に解放する。Host は現世代の受理・拒否の記録と復旧に必要な変更を一体で記録してから応答する。

下書き世代は manifest ID・パッケージ版とハッシュ・native schema・codec ハッシュ・manifest の `contractVersion`・共同編集 add-on の版・各 `OperationDeclaration.version` を固定する。順にパッケージ契約、共有機能の契約、個々の操作入力と意味の版を区別する。操作宣言が同じでも別パッケージ版の同席は拒否する。移行は製品 Host が新たに付与する管理権限とし、既存の writable からは導出しない。移行権限を持つ担当者が書き込みを止め、確定 snapshot を固定し、明示的に選んだ migration と新 codec を同じ QuickJS 隔離・累計予算で実行し、移行結果を検証する。元の版と移行結果を見比べて承認した時だけ、新世代へ原子的に切り替える。失敗時は旧世代を再開できる。未送信入力は新世代に自動再送しない。固定値と世代・revision は versionId に結び付けた新しい ConfirmedVersion の外側の保存メタデータ（ArtifactVersion と同じトランザクションの別レコード）に置く。ArtifactVersion.content とその contentHash は従来の native 内容だけを対象にする。

宣言のないパッケージで共有を開くと Host が開始を断る。利用者は単独編集を選べる。共有中の切断を契機に単独編集や内容全体の後勝ち保存へ切り替えない。draft.1 Host は未知の add-on を含む manifest 自体を拒否するため、単独編集にも旧 manifest の配布版が必要。draft.2 対応 Host 同士では、共同編集を optional として交渉可能にする案を検証する。これは draft.1 Host の登録規則を変更しない。

## カード例の受入条件

独立したブラウザー A・B と信頼された Host を使う。各拒否で live revision と保存版が変わらず、送信側には理由と本人の未反映入力が残ることを共通の判定とする。

| 前提・操作                                                                                          | 期待                                                                                                                                                                   |
| --------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A・B が別カードの名前を編集し A が Undo、同じタブを再読み込みして Redo                              | Host が再開 token を消費して session を引き継がせ、双方の画面で A の欄だけが戻り、Redo で再適用される。B の名前は保たれる。旧接続の書き込み・Undo・Redo は拒否される。 |
| 再読み込みと識別できない環境、または期限切れ・消費済み token で再開を求める                         | 再開を拒否して新規 session で開く。元の Undo 履歴は使えず、既存の接続は切れない。                                                                                      |
| 同じ欄を編集し A が先に確定する。A が元の値に戻した場合も試す                                       | B は stamp の不一致で競合する。                                                                                                                                        |
| A が削除したカードを B が編集中で、そこにカーソルがある                                             | B の送信は target-deleted。入力は残り、カーソルは orphan になる。                                                                                                      |
| 別カードを A・B が同時に並べ替える                                                                  | 先に確定した順序を保ち、もう一方は競合する。                                                                                                                           |
| A の追加と B の並べ替えを両方の確定順で送る                                                         | 追加が先なら B は競合し、並べ替えが先なら A のカードが末尾に加わる。                                                                                                   |
| A の追加後、B がそのカードを編集し A が追加を Undo                                                  | undo-conflict。B の編集とカードが残る。Redo の対象も増えない。                                                                                                         |
| 同じ ID のカードを2人が別の操作で追加                                                               | 後の追加は ID 使用済みで拒否される。                                                                                                                                   |
| 99枚から異なる ID を同時追加                                                                        | 先の追加で100枚になる。後の追加は枚数上限で拒否される。                                                                                                                |
| 受理応答を失い、再接続後に同じ要求を再送。拒否済みでも試す                                          | 元の receipt が返り、二重に適用されない。                                                                                                                              |
| 自分の操作 ID を異なる内容で再使用する。別途、所有外の名前空間の ID で送信・照会する                | どちらも同じ `protocol-error` と本文になり、他者の ID の存在は分からない。他者の receipt 照会は存在しない ID と同じ応答になる。                                        |
| 加算操作の受理直後に切断・世代切替・Host 再起動が重なる                                             | 再接続した Surface が旧世代の receipt を照会して受理済みと分かり、未送信一覧から外す。加算は1回だけ反映される。                                                        |
| 旧世代の receipt を7日の期限後に照会する                                                            | 「結果不明」と表示し、新世代へ自動再送しない。本人入力は残る。                                                                                                         |
| 1 session から毎秒10件・瞬間20件を超えて送る。別途、同一 actor が2タブで拒否を合計500件に到達させる | 超過分と停止中の要求は受付前に返り、世代の件数に加算されない。receipt 照会と既存要求の再照合は使える。                                                                 |
| 未送信入力を持って再接続する                                                                        | 現在の権限・対象条件を照合し、未反映入力を残す。                                                                                                                       |
| 入力中に閲覧権限を失う                                                                              | 配信と保存を止め、本人が書いた値だけを回収できる。                                                                                                                     |
