# 小説ワークスペースとDocumentの共存設計

設計案 v1、2026-10-29。`@editor-platform/document` の能力追加を提案する。[長編Document・Designページ構成](../novel-comic-design.md)と[長編Host契約](../authoring-contract.md)の後続案で、[漫画ワークスペース設計](../manga-creation/workspace-design.md)（#575）と同じ型を小説に当てはめる。新しい `novel` kindは設けず、小説専用の画面から同じDocument原稿を編集する。これは未実装の提案であり、既存機能の受け入れ記録ではない。

> **2026-11-14の注記：** この文書は当時（2026-10-29）の設計提案で、本文の「未実装」「未受け入れ」は当時の状態です。小説ワークスペースはその後実装し、2026-11-14に正式版として受け入れました。現在の機能と制限は[status](../status.md)の「長編Document・Designページ」、[長編Host契約](../authoring-contract.md)（縦書きEPUB/PDFの対象・拒否条件など）と検証記録を参照してください。

## 1. 採用を提案する判断

利用者には「小説」を独立した作成・編集の入口として見せる。内部では章ごとのDocument Artifact、一つのdraft、一つの編集sessionをそのまま使う。小説画面は章・シーンの並び、本文、通読、参照中の設定、提案の比較を中心に構成し、「Documentで詳細編集」から通常の書式・表・inspectorへ往復する。

| 選択肢                                   | 利点                                       | 判断                                                                   |
| ---------------------------------------- | ------------------------------------------ | ---------------------------------------------------------------------- |
| 通常Documentに小説用ボタンだけ追加       | 実装を小さく始められる                     | 縦書き・通読・文字数・参照が一般の書式設定に埋もれるため完成形にしない |
| 別kind・別Editorとして小説を作る         | 画面を自由に構成できる                     | text engine、IME、履歴、提案、出力が重複するため採らない               |
| 専用の小説画面と入口、共通のDocument原稿 | 執筆に合う画面と既存の編集能力を両立できる | 本案。漫画画面と同じく画面切替とデータ変更を分離する                   |

日本語組版（縦書き・ルビ・傍点・禁則）は、小説本文と漫画の吹き出しの両方で必要になる。content modelはEditorごとに分けたまま、配置計算だけをpureな共通helperとして設計する（§6）。

## 2. 現状と追加範囲

現行の根拠は[Host契約](../authoring-contract.md)、[M0検証](../verification/novel-comic/README.md)、[EPUB段階設計](../document-publishing-design.md)。過去の検証結果を今回再実行した結果として扱わない。

| 項目         | 調査時main                                                                                                       | 本案で追加するもの                                                     |
| ------------ | ---------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| 原稿・章     | 章ごとのDocument Artifact。章順はHostのID配列。chapter/scene専用entityはない                                     | 同じArtifactを開く小説画面。章・シーンentityは引き続き追加しない       |
| 部分改稿     | `documentText` / `findDocumentText` / `documentTextEditCommand`、`documentProposalDiff`、`ArtifactEditor` の採否 | 文単位の提案を小説画面の右ペインで比較する表示。採否の契約は変えない   |
| 注釈・移動   | `ElementAddress`、`resolveDocumentAddress`、`DocumentSurface.focusAddress`                                       | 読者パネル等の範囲指摘を注釈として並べる表示                           |
| 通読         | `@editor-platform/document/sequence` の `composeDocumentSequence`（最大128確定版）                               | 小説画面の通読表示。確定版の結合結果を読むだけで、正本として保存しない |
| 出力         | DOCX、水平EPUB 3（N2a）。縦書き・ルビは全体を拒否                                                                | 縦書きEPUB・縦書きPDFは§6の段階V3。それまで拒否のdiagnosticを保つ      |
| 組版         | 水平のみ。縦書き・ルビ・傍点・禁則は非対応                                                                       | 縦書き表示と編集、ルビ・傍点のinline、禁則（§6）                       |
| 文字数・照合 | なし                                                                                                             | 文字数のpure集計と、Hostが渡す表記辞書に照らしたdiagnostic（§7）       |

## 3. 参考にした道具と本案の判断

| 道具      | 参考にする操作                                                                                         | 本案での扱い                                                                                        |
| --------- | ------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------- |
| Scrivener | 原稿をシーン単位に分けるバインダー、分けた原稿を続けて読み書きする表示、コルクボード、スナップショット | 並びと状態はHost。続けて読む表示は `composeDocumentSequence` の通読、スナップショットは既存の確定版 |
| Nola      | 縦書きプレビュー、ルビ・傍点、企画・プロット・資料の型、TXT/Word/EPUB/PDF出力                          | 縦書き・ルビ・傍点はDocumentの能力として追加。企画・資料の型はワークフロー定義とHost                |
| CWStudio  | 縦書き、ルビ・傍点、画面分割、範囲を指定したAIの感想                                                   | 画面分割は小説画面の参照ペイン。AIの感想はHostの実行で、Documentは範囲注釈を表示するだけ            |

道具の内部形式や全操作を再現する提案ではない。AI生成・感想の実行、作品の進行管理はこのリポジトリに持ち込まない（リポジトリの開発方針）。

## 4. 利用体験と画面

### 作成・再開・切替

1. Hostの「新規作成 → 小説」で縦書き/横書きと章の数を選び、Document Artifactと初期章を一つの作成処理で用意する。途中の空Artifactを完成品として公開しない。作成導線はHostの追加実装。
2. 章を開き、本文を書く。Hostから渡された人物・場所・シーンカードの版付き参照を横に開ける。
3. 「Documentで詳細編集」で通常のツールバーとinspectorへ移る。同じ段落が選択された状態で続けられる。「小説へ戻る」で執筆画面へ戻る。
4. 比較中の提案は対象版が変わらなければ保持する。作者が本文を直した後の古い提案は再比較が必要になる。
5. 通読は確定版を結合して表示する。作業中のdraftを通読結果に混ぜない。

既存Documentを開いたときの既定は通常Document。章が複数あるだけで小説画面へ自動切替しない。画面の選択はHostのprivate view stateでありnative contentに入れない。縦書き/横書きの指定は原稿の表示設定として保存するか、Host view stateにするかを§11で決める。

### 小説画面の構成案

```text
Host: 作品 / 章名 / 保存状態 / 小説・Document切替 / 版・出力
┌─────────────┬───────────────────────┬─────────────────────┐
│ 章・シーン  │ 本文（縦書き/横書き） │ 参照：人物・場所・  │
│ の並び      │                       │ シーンカード        │
│ 状態        ├───────────────────────┤                     │
│             │ 執筆 / 通読           │ 提案の比較と採否    │
│ 文字数・目標│                       │ 範囲の指摘（注釈）  │
└─────────────┴───────────────────────┴─────────────────────┘
```

これは画面構成案であり、実装画面の画像ではない。左ペインの章・シーンの並びと状態はHostが渡し、Documentは表示と選択の通知だけを持つ。漫画画面（[#575 §4](../manga-creation/workspace-design.md)）と同じ3ペインの骨格にそろえる。

### 切替の不変条件

[漫画ワークスペース設計の切替の不変条件](../manga-creation/workspace-design.md)をDocumentにも同じ形で適用する。Artifact・draft・確定版を切替で変更しない、view切替をUndo履歴に積まない、Artifact単位のsessionを保つ、IME composition中は切替を保留する、read-onlyでは表示切替と閲覧だけを許す。縦書き⇔横書きの表示切替も同じ条件に従い、本文・選択範囲・注釈のaddressを変えない。

## 5. Editor・Host・ワークフローの責務

| 所有者                    | 責務                                                                                                   |
| ------------------------- | ------------------------------------------------------------------------------------------------------ |
| Document model / commands | 本文・ルビ・傍点・縦書き表示設定、text engine、IME、native履歴、提案の差分、文字数集計、出力projection |
| Document Surface          | 小説/通常の画面構成、縦書きの描画と選択、通読表示、注釈の表示、read-only表示                           |
| 消費Host                  | 作成入口、章順・シーン・状態、画面選択の保存、AI実行、提案の取得と採否の記録、来歴、表記辞書の供給     |
| ワークフロー定義          | 工程・成果物・項目・受入。画面の切替や組版の形式を所有しない                                           |

漫画（#575）と比べた分担は次のとおり。

| 区分             | 内容                                                                                                                                                         |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Hostで共通にする | 物語設定の正本、制作単位と受入、提案の対象ID・読んだ版、影響の伝播、AIの役割と来歴、作成入口。Editor Platformには持ち込まない                                |
| 同じ型で別に作る | 専用画面＋共通native原稿、`workspace` の選択、切替の不変条件、IDと順序の分離（シーンを章の子にしない／コマをページの子にしない）、通読表示、確定版からの出力 |
| 共通基盤の候補   | 日本語組版の配置計算（§6）。表記辞書の照合結果の形（§7）                                                                                                     |
| 小説特有         | 長い縦書き本文の編集、ルビ・傍点のinline、文字数・原稿用紙換算、範囲注釈による読者の指摘、縦書きEPUB/PDF                                                     |
| 漫画特有         | コマ分割の木・共有境界・polygon、見開き、ペン・Raster、吹き出し、通常Designとの往復                                                                          |

画面選択の最小API案は、既存 `DocumentSurfaceProps` にoptionalな `workspace?: 'document' | 'novel'` を足す形とする。省略時は従来のDocument。漫画の `DesignSurfaceProps.workspace` 案と同じ考え方で、汎用workspace登録frameworkは作らない。これは未実装の型案である。

## 6. 日本語組版の段階と共通helper案

| 段階 | 内容                                                                                 | 受入の観点                                                                           |
| ---- | ------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------ |
| V0   | ルビ・傍点のinline model（親文字範囲と読み）。横書きで表示・編集・提案差分・DOCX出力 | 親文字の途中で切る編集、IME中の入力、Undo、提案差分での表示、DOCXへの対応/近似の報告 |
| V1   | 縦書きの表示・選択・caret・IME。縦中横は数字2桁まで                                  | 選択範囲とaddressが横書きと一致する、IME候補窓の位置、read-only                      |
| V2   | 禁則（行頭・行末）とぶら下げの配置計算                                               | 同じ入力で同じ改行位置、表示と出力の差をdiagnosticで示す                             |
| V3   | 縦書きEPUB 3、縦書きPDF                                                              | EPUBCheck、独立readerでの表示、水平EPUB（N2a）の回帰                                 |

V2の配置計算は、Documentの本文とDesignの吹き出しの文字の両方から使えるpureなhelperとして設計する。入力は文字列・ルビの範囲・行の長さ・方向、出力は行分割と位置のみとし、どちらのcontent modelにも依存しない。Designの縦書き吹き出しへの適用は漫画側の段階で判断する。

## 7. 文字数と表記の照合

文字数はDocument contentからのpure集計とし、数え方を引数で明示する。既定は空白と改行を含めない、ルビは親文字だけを数える、hiddenを除く。原稿用紙換算（20×20など）は禁則を考慮しない近似として返し、近似であることを結果に含める。目標の管理はHostが持つ。

表記の照合は、Hostが渡す辞書（正しい表記と使わない表記の対）に照らして、該当範囲のaddressと候補をdiagnosticとして返す。自動置換はしない。直すときは既存の `documentTextEditCommand` による提案として作者が採否する。辞書の正本と、どの用語を照合するかはHostとワークフロー定義の項目（用語）が持つ。

## 8. 提案・注釈・来歴

AIの提案は既存の `ArtifactEditor` の propose/accept/reject と `documentProposalDiff` を使い、新しい履歴やAI runtimeを追加しない。外部の設定を読んだ提案は `previewHostProposal` / `applyHostProposal` と `checkProposalReads` にexact reference versionsを渡す。

来歴（どの段落が作者の文か、AIの提案を採ったものか）はHostが提案と採否の記録から作る。Documentはcontentに来歴を保存しない。Hostが記録できるよう、採用結果で変わった要素IDを既存の経路で取得できるかを実装時に確認し、足りなければ読み取り専用の情報として追加する。

読者パネル等の範囲指摘は既存の注釈として付け、本文を変えない。削除された範囲の注釈は既存どおりOrphan/Outdatedとして表示する。

## 9. 宣言能力と非対応

- 共有編集はDocumentの既存の宣言subsetに限る。ルビと傍点は通常の書式としてstepで共有する。縦書きは原稿の設定で、本文のstepでは変わらない（2026-11-14に拒否をやめた）。
- 章をまたぐtransaction、章・シーンentity、Story Graph、作品の進行管理は追加しない。
- 縦書きEPUB/PDFはV3まで拒否のdiagnosticを保ち、水平で近似出力しない。（V3で対応済み。2026-11-14に縦書きPDFの表・画像・図・コード・リスト、EPUBの画像・リンク・フォント・縦横混在も対応。）
- 新規の性能測定・tuningは現在の保守条件に従い、本案に含めない。

## 10. 実装順と受入計画

Pure model・validator・command（ルビ・傍点、文字数、照合）→ 通常Document Surfaceでの表示 → `workspace: 'novel'` の画面 → 縦書き → 禁則 → 縦書き出力、の順に進める。各段階の受入は下表の NV01〜NV08 で固定する。

| 条件 | 内容                                                                                          |
| ---- | --------------------------------------------------------------------------------------------- |
| NV01 | 3章×複数シーンのfixtureで、小説画面と通常Documentを往復しても原稿・版・選択・Undoが変わらない |
| NV02 | IME composition中とread-onlyで切替・提案採用・保存が保留または拒否される                      |
| NV03 | ルビ・傍点を含む本文の部分改稿提案が差分で表示され、採用が1回のUndoで戻る                     |
| NV04 | 文字数集計が数え方の引数に従い、同じ入力で同じ結果を返す                                      |
| NV05 | 表記照合が自動で本文を変えず、提案として採否できる                                            |
| NV06 | 通読表示が確定版だけを結合し、draftを含まない                                                 |
| NV07 | 縦書きと横書きで同じaddressが同じ範囲を指す                                                   |
| NV08 | 縦書きEPUB 3がEPUBCheckを通り、独立readerで表示できる                                         |

## 11. 残る判断と後続範囲

- 縦書き/横書きの指定を原稿の表示設定として保存するか、Host view stateにするか。出力で使うなら原稿側に持つ案が有力。
- ルビのinline modelを既存のmarkで表すか、新しいinline nodeにするか。DOCX・EPUBでの表現と提案差分の扱いで比較する。
- 禁則helperをDesignの吹き出しと共有する時期。漫画の縦書き対応の段階と合わせて決める。

Host側の制作単位・提案の記録・来歴と、ワークフロー定義の工程は、それぞれ消費Hostと定義の側で扱う。
