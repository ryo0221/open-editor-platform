# 文書の記載方針

文書は、読む人の目的と情報の寿命に合わせて置きます。同じ仕様の本文は一か所で管理し、ほかの文書からは短い要約とリンクで参照します。文書を探す入口は[ドキュメント一覧](README.md)です。

## どこに何を書くか

| 記載先                                                                                   | 書く内容                                                                | 詳細の置き場所                                                 |
| ---------------------------------------------------------------------------------------- | ----------------------------------------------------------------------- | -------------------------------------------------------------- |
| [root README](../README.md)                                                              | プロジェクトの概要、最短の起動手順、保存の注意、主要な入口              | 操作・仕様・検証の詳細は各文書へリンク                         |
| [docs/README.md](README.md)                                                              | 目的別の文書案内                                                        | 案内に必要な一行説明とリンク                                   |
| [status.md](status.md)                                                                   | 現在の対応範囲、非対応、既知の制限と根拠への入口                        | 機能契約と検証記録へリンク                                     |
| `docs/*-guide.md`、機能別の利用文書                                                      | 利用者の操作手順、入力、出力、復旧方法、制限                            | 例：[Geo](geo-guide.md)、[テンプレート](template-authoring.md) |
| [embedding.md](embedding.md)、[host-integration.md](host-integration.md)                 | Hostが渡すAPI・adapter、保存、履歴、権限、組み込み例                    | 機能固有の契約を参照                                           |
| `docs/*-contract.md`                                                                     | 現在のデータ・APIの約束、不変条件、責任境界、互換性、上限、拒否時の動作 | 実装済みと提案段階を明記                                       |
| `docs/*-design.md`、機能別の設計文書                                                     | 構成、代替案、未決事項、段階的な実装計画                                | 採用後の仕様は対応する契約へ反映                               |
| `docs/decisions/NNN-*.md`（ADR）                                                         | 長く残す設計判断、理由、比較案、影響                                    | 現在の仕様・関連ADRへリンク                                    |
| [developer-guide.md](developer-guide.md)、[editor-development.md](editor-development.md) | 開発の入口と実装手順                                                    | 詳細な仕様は機能契約へリンク                                   |
| [editor-acceptance.md](editor-acceptance.md)、`docs/*verification*.md`の計画文書         | 受け入れ条件、シナリオ、実施前に固定する条件                            | 実行結果は検証記録へ                                           |
| `docs/verification/<topic>/README.md` と同directoryの補足                                | 変更の再現、検証source・環境・コマンド・対象・結果・未実施・証拠の所在  | [検証報告テンプレート](editor-verification-template.md)を利用  |
| `docs/history/`                                                                          | 整理前の実装報告や過去の作業指示                                        | 当時の記録として保存し、現在の仕様はリンクで案内               |
| [AGENTS.md](../AGENTS.md)                                                                | 作業開始時に守る継続的な開発ルール、必読文書への入口                    | 機能ごとの進捗や検証件数は各記録へ                             |
| [repository-assets.md](repository-assets.md)、資産・証拠の管理文書                       | 環境、資産、CI、生成物の保持・取得・再生成                              | フォント・証拠の原本や生成物はGit外                            |
| Issue / PR                                                                               | 要望、未解決事項、変更理由、レビュー、今回実施した検証                  | 採用した仕様と利用方法はリポジトリの文書へ反映                 |

package内のREADMEには、そのpackageを単独で使うための入口、依存、固有のbuild・設定・制限を書きます。全体の起動手順や作業履歴は複製しません。コードのコメントには局所的な判断理由や不変条件を、公開APIのコメントには呼び出し条件・戻り値・失敗条件を記載し、長い利用手順はガイドへリンクします。

`status.md`は各機能の現在の要約を更新します。テスト件数・commit hash・レビュー経緯の追記は検証記録で行います。READMEの更新は、概要・起動・主要な導線が変わる場合に行います。

## 変更に応じた更新先

- 操作や出力が変わる：対応する利用ガイドを更新し、必要ならHost/API契約とstatusの該当箇所を更新する。
- schema・API・権限・履歴・上限が変わる：機能契約と互換性の説明を更新する。長く残す選択理由はADRに書く。
- バグやレビュー指摘を直す：現在の説明に変更が必要なら修正する。再現と確認結果は同じtopicの検証記録にまとめ、READMEやAGENTSには追加しない。
- 新しいEditorを作る：[設計テンプレート](editor-proposal-template.md)で対象を宣言し、契約・利用ガイド・検証記録を用意する。文書一覧とstatusに入口を追加する。
- CI・資産・公開手順が変わる：対応する運用文書と設定を更新する。個別作業の進捗や停止・再開の履歴は、その作業の記録へ書く。
- 文書だけを直す：リンク・記載コマンド/API・書式・公開対象を確認する。実施していないアプリのテストを今回の結果に含めない。

## 命名と履歴

新規の文書は内容を表す名前にします。関連文書が複数ある機能は`docs/<feature>/`へまとめ、最初に読む文書を明示します。小さな追補は同じtopic内へ置き、レビューコメントごとに新しいトップレベル文書を増やしません。

既存のIssue番号付き文書や`docs/animation/`、`docs/geo/`、`docs/extension-76/`などは参照を維持します。過去の検証結果には対象sourceを残し、再実行は日付・source・範囲を添えて別の結果として記録します。失敗・未実施を後の成功で書き換えません。文書を移動するときは参照元と相対リンクを確認します。

将来の計画、実装済み、検証済み、公開・配布への反映済みを区別してください。`latest`や「完了」だけで範囲を表さず、該当する契約・検証記録への参照を付けます。

## 公開用文書

公開文書も開発元で保守し、レビュー済みsnapshotへ含めます。新しいガイドや検証記録を自動的に公開対象だと判断せず、export policyの収録対象・相対リンク・残留検査を確認します。

README、AGENTS、status、ライセンスなどは公開用overlayが適用されます。共通ガイドを更新する場合は、開発元と公開snapshotの両方で参照先が成立することを確認します。製品固有の試用、内部の承認・停止条件、非公開sourceとの対応表は公開用文書から参照しません。

公開用overlayの修正と実際の公開同期は別の作業です。snapshotの生成・検査では必須のセキュリティゲートを通し、公開・配布への反映はその作業の権限と手順に従います。
